# Whimway native migration audit

Audit date: 13 October 2026. Repository: `https://github.com/Hearthlane/Whimway`, baseline commit `cc9a129` (`Allow the exact Codespaces preview origin and forwarded app requests`), working branch `codex/native-mobile-experience`. The existing checkout was clean before implementation; repository instructions were read. This document separates baseline findings, implementation decisions and evidence still required.

## Existing product and architecture

The repository is an existing Next.js 16.4 / React 19.3 App Router application, not an empty project. Its routes include Explore, Create, Your Plan, Saved, Profile, public shared-plan viewing, auth callback, Privacy and Terms. It already has Outfit and DM Sans, the requested palette, original editorial illustrations and responsive web navigation. The most valuable work is the backend and deterministic planning safeguards; it should be preserved.

## UX findings that drove implementation

The homepage clearly suggests enjoyable outings and its working destination/prompt controls do fit in the first 390 × 844 viewport. The editorial headline uses much of that space, while illustration, inspiration and manifesto extend the settled fixture-preview page to 2332 pixels. Native Explore should retain the recognizable tone while making the destination/prompt the first visual task and keeping decoration subordinate.

Create has three long sections presented together: location/radius/Area Lock, prompt and ten interest chips, then six scheduling/group/budget/transport controls. Dietary/accessibility/currency and two anchors sit in an expanded advanced section. Rendered at 390 pixels with preview available, Create is approximately 2248 pixels tall with seventeen input/select/textarea elements in the document; the large map/unavailable-map state appears before the location question. A user can technically generate after typing/selecting an area and tapping generation because defaults exist, but the page communicates a full questionnaire and the generation action is several screens down. Technical geographic controls have the same prominence as the decision to explore. Optional questions do not offer explicit Skip. This creates unnecessary reading and scrolling before value.

The prompt reaches the AI only during final generation. It does not prefill the controls; form defaults are treated as explicit constraints, so a user can describe a date or budget and still confront those fields or a prose/form conflict. The native flow must parse supplied facts first, distinguish defaults from user answers, skip known questions, preserve Back state, and allow generation early.

The itinerary already has meaningful edit operations and synchronized map selection. However, controls, cautions, metadata and remix chips compete with the story of the day. Venue cards should prioritize time, place, duration, price uncertainty and one contextual menu. Existing photographs are real attributed provider content when available; illustrative fallback must remain clearly distinguishable. Do not introduce unrelated location photos.

The baseline navigation action opens Google Maps externally. It has no dedicated active outing, completed/skipped stop state, foreground location-to-stop routing or scheduled reminders. A native Day Mode should make progress explicit and show route preview, the next destination, estimates and permission-denied recovery. It must not imply maneuver or arrival guidance that it does not implement.

Saved and Profile already support guest persistence and optional accounts. Account creation must remain deferred. Device plans need explicit refresh/error recovery on reopen; preferences need an opt-in application model. Notifications should be offered after results, with permission asked only after selecting reminders.

## Native stack and navigation decision

Use Expo SDK 57, React Native 0.86 and React 19.2.3, with Expo Router, Reanimated, Gesture Handler, safe areas, foreground Location, local Notifications and Haptics. The initial check selected `expo@57.0.28`; official compatibility guidance changed overnight and source `99228dd` aligns Expo to 57.0.29, Constants to 57.0.22, Linking to 57.0.13, Notifications to 57.0.23 and Router to 57.0.27. Alignment, Doctor 21/21 and native compilation subsequently passed for that SDK set; current 984 app revisions need their own native reports. Expo recommends compatible package installation with `expo install`; the SDK table requires Node 22.13+, Android 7+ / API 36 and iOS 16.4+ / Xcode 26.4+. [Expo SDK reference](https://docs.expo.dev/versions/latest/)

Google's current React Native Navigation SDK is beta; `0.17.3` requires React Native `>=0.87.0`, beyond Expo 57's RN 0.86.3. Its README requires the New Architecture and Kotlin 2.3.21 override and directs earlier RN versions to `0.16.3`. The older beta advertises RN 0.79+ with tested versions through 0.83.1; this does not establish that RN 0.86 is incompatible. [0.17.3 requirements](https://raw.githubusercontent.com/googlemaps/react-native-navigation-sdk/v0.17.3/README.md), [0.16.3 requirements](https://raw.githubusercontent.com/googlemaps/react-native-navigation-sdk/v0.16.3/README.md)

The older version cannot be added unchanged to this app's Google map stack. On iOS, its podspec pins GoogleNavigation 10.13.0, which requires GoogleMaps 10.13.0. Installed react-native-maps 1.27.2 pins GoogleMaps 9.4.0 and Utils 6.1.0; the latter also requires GoogleMaps `~>9.0`. Those constraints cannot resolve together. This is a dependency conflict established from the published specifications, not a failed integration build. [Navigation podspec](https://raw.githubusercontent.com/googlemaps/react-native-navigation-sdk/v0.16.3/react-native-navigation-sdk.podspec), [GoogleNavigation dependencies](https://raw.githubusercontent.com/CocoaPods/Specs/master/Specs/3/d/1/GoogleNavigation/10.13.0/GoogleNavigation.podspec.json), [RNMaps podspec](https://raw.githubusercontent.com/react-native-maps/react-native-maps/v1.27.2/react-native-maps.podspec), [Utils dependencies](https://raw.githubusercontent.com/CocoaPods/Specs/master/Specs/3/5/e/Google-Maps-iOS-Utils/6.1.0/Google-Maps-iOS-Utils.podspec.json)

On Android, Navigation bundles Maps classes and its official sample excludes transitive `play-services-maps` to avoid duplicate copies. Coexistence would need exclusions/substitution plus compilation and API/ABI testing; no further specific ABI incompatibility has been proven. A migration to Navigation's MapView, a changed map-provider strategy, or a future aligned Expo/SDK stack remains possible. This release therefore provides native map/route preview and explicitly leaves full turn-by-turn unavailable; an older-SDK migration is a separate unverified option, not a blanket RN incompatibility claim. [Official Android exclusions](https://raw.githubusercontent.com/googlemaps/react-native-navigation-sdk/v0.16.3/example/android/build.gradle)

Navigation requires a billed Google Cloud project and enabled/restricted platform keys. Route destination requests are billed under Navigation Request; guidance and subsequent route deviations do not add separate destination charges. Confirm the project's current agreement, quotas and prices before activation. [Google Navigation billing](https://developers.google.com/maps/documentation/navigation/android-sdk/pricing)

The SDK's policies require first-use terms/disclaimers, intact attribution and safe driving UI; overlays must not obscure guidance or distract drivers. Public privacy/terms and provider-content handling require review before release. The existing app is an outing planner, not a driver safety system. Background location is not justified for the initial foreground preview implementation and must not be requested. [Android policies](https://developers.google.com/maps/documentation/navigation/android-sdk/policies), [iOS policies](https://developers.google.com/maps/documentation/navigation/ios-sdk/policies)

## Implemented architecture and visual review

The native project uses actual React Native screens, Expo Router navigation and native modules; it does not embed the existing site in a WebView. The Next frontend remains available. Shared Zod types, planner/provider rules and API response contracts stay in the original repository. Mobile adds a bounded HTTP client, verified bearer auth, local reference persistence, revision-aware response commits, foreground location, native map rendering and local reminder scheduling. Secrets and costly discovery/AI/routing calls remain on the server.

Explore puts destination, Near me, an optional prompt and the generation entry before the decorative route illustration. Adaptive planning asks only unanswered optional questions and preserves explicit choices; early generation applies the validated defaults in the destination timezone. Profile preferences apply only when enabled, distinguish budget currencies and preserve local edits when account settings conflict. Unknown provider prices remain unknown rather than being fabricated or converted silently.

The itinerary uses a timeline and contextual menus instead of a page of competing edit controls. Replacement, add/remove, reorder, lock, duration/budget/mode edits and remix all use server operations. Day Mode keeps progress explicit and persisted, uses independent walking/driving guidance to the next pending stop, and distinguishes remaining activities from remaining travel. It does not simulate maneuvers or automatic arrival. Reminders use destination-offset timestamps, suppress past/completed/skipped events, and cancel prior identifiers when schedules change.

The actual RN Web screen preview is captured in `docs/screenshots/mobile-preview`; it is useful for typography, hierarchy, contrast, input flow, local persistence and backend requests. Native map placeholders explicitly describe their limitation and list selectable stops; the web-only fallback is scroll-contained so fixed map panels remain usable. Browser preview cannot validate native map attribution placement, GPU rendering, OS permissions, notification delivery, VoiceOver/TalkBack, gestures or startup performance. Those checks stay in the native release checklist.

The local Metro development bundle took about 97 seconds to transfer during parallel development work on this Windows host. This is a tooling observation, not a measured native performance result. Browser regressions now build an official `expo export --dev --platform web` artifact in ignored `dist-qa` and serve it through localhost QA tooling. This preserves the source's development fixture switch without changing production behavior. Metro excludes generated build/test/screenshot directories to avoid unnecessary watch activity. Production Android/iOS Hermes and web exports are verified separately.

Expanded browser accessibility checks cover Explore, Saved, Profile, adaptive planning, itinerary, the selected coral marker and active Day. Review fixed the unnamed Day progress indicator, an overflowing enlarged-text chip and scrolling inside the browser map fallback. Current captures include five portrait sizes and a clearly labeled 200% browser text approximation. Source 992 Android keyboard/sheet recovery, portrait/progress and actual fontScale 2.0 subsequently passed; current 984 display-source OS checks, small-device native safe areas and assistive interaction remain open.
